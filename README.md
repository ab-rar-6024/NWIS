# eRTMAC-NWIS — Nearby Wells Intelligence System

Smart India Hackathon 2026 · Problem Statement **SIH26121** · Oil India Limited
*An AI-powered offset-well knowledge and decision-support platform for drilling operations.*

The system gives a drilling engineer the institutional memory of every nearby well: it reads the old
reports, finds the wells around the one being drilled, lines them up by depth and formation, and warns
the crew **before** the bit reaches a depth where neighbours had trouble.

> **Data disclosure.** No Oil India data was available, so the demo runs on a **synthetic** field
> (46 fictional wells — 2 held back for the live-upload demo — about 1,700 report pages, drilling logs) generated by `backend/nwis/synth`. Hazards in
> that field follow spatial rules (a fault zone with losses, an overpressure pocket, a coal-rich
> stuck-pipe area) so that neighbouring wells genuinely predict each other. Every accuracy number below
> is measured on this synthetic data — it demonstrates the pipeline, **not** field accuracy. The
> ingestion path is the real one: point it at real WCR/DDR PDFs and eRTMAC exports.

## Why this build, not another dashboard

Three things most "AI dashboard" submissions for this kind of PS skip, because a judge who has seen many
of them will look for exactly these:

1. **A quantified answer to "so what"**, not a slide claim. The **Why it matters** landing page runs a
   real leave-one-well-out backtest: every well's own reports are hidden, hazards are forecast from its
   neighbours only, and the result is checked against what actually happened to that well. The coverage
   percentage and the rupee estimate recompute live if you change the search radius — they are not
   hard-coded numbers picked for a demo.
2. **Alerts that show their evidence.** A "48% risk" score with nothing behind it is not something a
   drilling engineer will act on. Every model-generated alert now names the offset wells that drove it, on
   top of the source sentence every extracted event already links back to.
3. **A feedback loop, not a one-shot script.** On the Live monitor, the engineer marks each alert
   *Accurate* or *False alarm*. That is exactly the labelled data a retraining pass would use, and the
   running agreement rate is visible in the page header — the system is shown improving with use, not just
   running once.
4. **A named physics diagnostic, and a measured answer to "is live monitoring worth it."** The **Why it
   matters** page shows, hazard by hazard, how much AUC the model gains from adding live drilling signals on
   top of offset-geometry knowledge alone — both are the same trained model on different feature subsets, not
   a comparison against a hand-written formula we don't have code for; the number is computed live from
   `/api/model/metrics`, not asserted. Separately, the live monitor computes **Teale's Mechanical Specific
   Energy** from first principles (the well's own planned casing programme gives the bit diameter at every
   depth) and feeds it into the model as a real feature, not just a chart — though its individual contribution
   to accuracy hasn't been isolated in its own ablation, only observed to correlate with real stuck-pipe zones
   in the live demo.

## Two audiences, one page: Simple / Technical

The dashboard opens in **Simple mode**: plain-English page intros, jargon (MD, TVD, SG, NPT, prevalence, …)
underlined and explained on hover instead of assumed, and the densest panels (the well-log correlation chart,
the six live sensor charts, the AI model's probability gauges, the AUC/precision table) collapsed behind a
"show technical details" toggle rather than shown by default. A **Simple / Technical** switch in the top bar
(`frontend/src/lib/uiMode.tsx`, persisted per browser) expands everything for a technical judge without
changing a single number underneath — same data, same live queries, just how much of it is shown by default.
This exists because a dashboard only a specialist can read fails the "understand it in 90 seconds" test that
actually decides scores.

## Quick start (Windows / PowerShell)

Prerequisites: Python 3.11+, Node 20+. To put this online instead of running it locally, see
[DEPLOY.md](DEPLOY.md) (frontend on Vercel, backend on Render — Vercel alone can't host the backend, since it
needs a persistent process for the SQLite file and the live-monitor's in-memory sessions/SSE stream).

```powershell
./setup.ps1        # venv, dependencies, synthetic data, ingestion (incl. OCR), model training, frontend build  (~5 min)
./start.ps1        # serves API + dashboard on http://127.0.0.1:8000
```

Manual steps, if you prefer:

```powershell
python -m venv .venv ; .venv\Scripts\pip install -r backend\requirements.txt
cd backend
..\.venv\Scripts\python scripts\build_dataset.py     # synthetic PDFs + logs  -> data/raw, data/samples, data/truth
..\.venv\Scripts\python scripts\ingest_all.py        # PDFs -> OCR/NLP -> SQLite (data/nwis.db)
..\.venv\Scripts\python scripts\train_model.py       # risk models -> data/models
cd ..\frontend ; npm install ; npm run build         # dashboard -> frontend/dist
cd ..\backend  ; ..\.venv\Scripts\python -m uvicorn nwis.api:app --port 8000
```

Development mode: `npm run dev` in `frontend/` (port 5173, proxies `/api` to 8000).

## Suggested 3-minute demo

1. **Why it matters** (landing page) — open with the backtest KPIs, then move the rig-rate and
   avoidance-rate sliders to show the rupee estimate is computed from adjustable assumptions, not fixed.
2. **Nearby wells** — active well MRH-17 in red; drag the radius slider and watch offsets appear.
3. **Correlation** — dashed predicted tops, offset events by hazard lane, shaded forecast bars on the
   target well; click any marker to see the *source sentence from the report* and comparable events.
4. **Live monitor** — *Start replay*. Watch the look-ahead strip; alerts fire hundreds of metres before
   the bit reaches each hazard, with the offset wells named on model alerts and the action that worked

5. **Documents & model** — click `DGR-15_WCR.pdf` then `DGR-15_DDR.pdf` under *Demo reports*: a new well
   appears with its extracted events, formation tops and confidence. Four of the loaded reports are

## Architecture

```
PDFs (WCR/DDR, text or scanned) ─▶ pdf_text.py ─▶ documents.py ─▶ events.py (NLP) ─▶ ingest.py ─▶ SQLite + FTS5
eRTMAC / DB exports (surveys, logs) ────────────────────────────────────────────────────▲
                                                                                         │
kb.py (trajectories, tops, events)  ─▶ analytics.py (top prediction, hazard zones, risk)─┤
features.py + risk_model.py (GBM)   ─▶ live.py (replay/push, alerts, SSE) ─▶ api.py (FastAPI) ─▶ React dashboard
```

Key design decisions

* **Distance between wells** is the closest horizontal approach over the depth interval both wells cover,
  computed from minimum-curvature trajectories — a directional well can be "near" at depth while far at surface.
* **Stratigraphic depth axis.** Events are mapped to a formation-relative depth so a mud loss 60 m into the
  Sylhet Limestone in one well is comparable to the same interval in another, regardless of structural dip.
* **Formation tops for the active well** are predicted from offsets with a weighted plane fit (captures
  regional dip) and carry an uncertainty (σ) shown in the UI.
* **Negations and contingencies** ("No losses observed", "kept LCM ready as a precaution against losses")
  are rejected by the extractor; multi-sentence incidents are grouped into one event with actions and outcome.
* **A DDR mention and a WCR mention of the same incident are merged** (depth-tolerant), raising confidence
  and combining fields; day-level depths (no explicit depth in the text) are flagged as approximate.
* **The model never sees its own well's events** (leave-one-well-out offset features) and is validated with
  cross-validation grouped by well.
* **Q&A is retrieval-only**: answers are assembled from recorded events and cite their sources — no generative guessing.
* **Mechanical Specific Energy (Teale's formula)** is derived from first principles in SI units — bit area from
  the well's own planned casing programme (`kb.Trajectory.hole_diameter_at_md`), not an imperial "field units"
  shortcut constant — and feeds the risk model as a real feature (`features.teale_mse_mpa`), not just a chart.

## Measured results (synthetic data)

Reproduce with the scripts in `backend/scripts/` (`eval_extraction.py`, `eval_live.py`, `eval_model_alerts.py`,
`train_model.py`).

| Check | Result |
|---|---|
| Event extraction from daily reports (`eval_extraction.py`) | P 0.99 · R 0.97 · F1 0.98; median depth error 0.3 m; NPT matched exactly 326/326 |
| Completion reports alone | P 1.00 · R 0.75 (the generator omits 20 % of events from WCRs by design; scanned pages read at 0.97 OCR confidence) |
| Consolidated database vs ground truth (43 wells, 398 events) | P 0.987 · R 0.987 · F1 0.987 |
| Formation-top prediction for the active well | mean abs. error ≈ 14 m, max ≈ 23 m across the 9 tops |
| Risk model, 5-fold CV grouped by well, with MSE as a feature (`train_model.py`) | AUC: mud loss 0.74 · kick 0.96 · stuck pipe 0.91 · overpressure 0.97 · torque spike 0.88 (36 features) |
| Value of offset knowledge (AUC using **only** neighbour data, no live signals) | mud loss 0.68 · kick 0.90 · stuck pipe 0.78 · overpressure 0.93 · torque 0.81 |
| Live replay of the active well (`eval_live.py`) | all 15 real events warned in advance; median lead **326 m** (any alert); live-signal/model alerts alone: 15/15 within 100 m; medium/high look-ahead zones: 61 % contain an event of that type, covering 13/15 events |
| Fleet-wide leave-one-well-out backtest (`/api/impact`, shown on the **Why it matters** page) | 43 wells cross-checked, each with its own reports hidden: **60 %** of past incidents and **57 %** of recorded downtime (≈2,964 h) occurred at a depth the system would have flagged from neighbours alone |
| Extraction on reports **never seen while building the extractor** (`BRS-15`, `DGR-15` — held out of `data/raw`, never scored by `eval_extraction.py` during development) | P 0.91 · R 1.00 · **F1 0.95** — close to the 0.99 tuned-set score, which is the honest check against overfitting the extractor to its own generator |
| Model alerts by *episode*, not by depth sample (`eval_model_alerts.py`) — precision/recall as a driller would actually experience it | ~1.4–4.6 alert episodes per well per hazard, 0.7–1.9 false alarms per well; **49–69 %** of episodes match a real recorded event (episode precision); **79–100 %** of real events get at least one matching alert (event recall) |
| Live signals added on top of offset-geometry knowledge alone — both are the same trained model, just given a different feature subset; not a comparison against another team's non-learned formula, which we don't have code for (shown live on the **Why it matters** page) | **+0.04 to +0.13 AUC** per hazard from adding live signals, average **+0.07** — measured, not assumed; quantifies whether the live monitor is worth building on top of a static offset map |

Honest reading of these numbers: on synthetic data the live signals carry strong short-range precursors
(that is how the generator injects them), so the model with live signals is only slightly better than the
signals alone. The distinctive value of neighbour knowledge is the **long-range** warning (hundreds of
metres, before any signal exists), which the look-ahead zones provide. On real data, expect lower absolute
numbers — and report the episode-level precision/recall above, not AUC, when a technical reviewer asks how
often the model is wrong: AUC alone flatters a rare-event classifier.

## API (selected)

`GET /api/wells` · `/api/wells/{id}/offsets?radius_km=` · `/api/wells/{id}/correlation` · `/api/wells/{id}/lookahead?md=&window=`
· `/api/wells/{id}/risk-profile` · `/api/impact?radius_km=&min_prevalence=` (fleet backtest, cached) · `/api/search?q=`
· `/api/lessons` · `POST /api/ask` · `POST /api/documents/upload` · `GET /api/live/{id}/stream` (SSE)
· `POST /api/live/{id}/control` · `POST /api/live/{id}/alerts/{alert_id}/feedback` (`{"status": "confirmed"|"dismissed"}`)
· `GET /api/live/{id}/feedback-stats` ·
**`POST /api/live/{id}/sample`** — the integration point for a real eRTMAC feed: push one depth-based sample
(`md, rop, wob, rpm, torque, spp, flow_in, flow_out, pit_delta, mw, gas, overpull`) and the same alert engine runs.
Interactive docs at `/docs`.

## Moving to real data — what changes

* Extend `FORMATION_LEXICON` in `nwis/config.py` with the basin's stratigraphy.
* Real DDRs will phrase things differently: add trigger patterns/lexicon entries in `extraction/events.py`
  (each pattern is a small regex with tests in `tests/test_extraction.py`) and re-run `eval_extraction.py`
  on a labelled sample of real pages — expect to tune before trusting recall numbers.
* Replace the CSV loaders in `ingest.py` (`load_survey`, `load_logs`) with connectors to the drilling and
  mud-logging databases; point eRTMAC at `POST /api/live/{id}/sample`.
* Retrain the model (`train_model.py`) on real history; review the alert thresholds it stores.

## Known limitations

* Extraction is rule-based: precise and auditable on the phrasing it knows, but it will miss unfamiliar wording.
* OCR of scanned pages drops some spaces/reorders lines; the parser tolerates this, but recall on poor scans is lower.
* Formation-top prediction assumes smooth structure; faults between wells are not modelled.
* One live well at a time is exercised in the demo; sessions, alerts and operator feedback are held in
  memory and reset when the server restarts (the `feedback` column on the `alerts` table is there for when
  sessions are made durable).
* The dashboard's basemap uses OpenStreetMap tiles and needs internet; everything else works offline.
* Mechanical Specific Energy assumes the bit is in the hole size the planned casing programme says it should
  be; an unplanned bit change, sidetrack, or hole opener mid-run isn't tracked, so MSE would be computed
  against the wrong diameter until the plan is updated.
* There is no field-usable UI mode (large touch targets, high-contrast display for direct sunlight/gloves) —
  the Simple/Technical toggle solves for technical depth, not physical rig-floor conditions; a separate mode
  would be needed for that.
